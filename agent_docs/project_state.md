## Recently shipped

- **PR #253 — C1 chat-stream heartbeat to keep large-model cold-loads alive — merged `6cfae14` (2026-05-10).** No new release tag (cross-OS UX fix folds into next ship). Closes the qwen3:14b chat-stall half of the v1.3.22 mac field-test report (M12 closed the orthogonal "no fail message" half). **Root cause:** server flushes `start` frame immediately, so Mac URLSession's 180s `timeoutIntervalForRequest` (per-packet timer, set in MAC39) is bound by "time to Ollama's first streamed token" — a 14b model mmap-load on USB SSD can exceed 180s, fires `NSURLErrorTimedOut` mid-load. Inner `HttpClient.Timeout=100s` doesn't apply (with `ResponseHeadersRead`, headers come back fast and the timer becomes irrelevant). Windows runner doesn't have this layer — it calls `IChatService` in-process, no URLSession — so the symptom only ever surfaced on Mac. **Fix shape:** server-side heartbeat. New `IChatService.FirstTokenPending(int seconds)` event. `ChatService.SendPromptStreamingAsync` wraps the streaming loop in a `Task.Run` heartbeat that fires the event every `HeartbeatIntervalSeconds = 20` until `Interlocked.Exchange(ref firstTokenSeen, 1) == 0` flips. `/chat/stream` subscribes to the event for the duration of one request and forwards each tick as `{type:"loading", elapsedSeconds:N}` NDJSON. Mac (`chatStreamDidReceiveLine`) handles the new frame type — paints `Loading <model>… NNs` in the title-strip status; the `token` case clears it via `hasPrefix("Loading ")` gate when the first token arrives. Windows (`MainWindow.xaml.cs`) subscribes to `FirstTokenPending` directly (in-process), Dispatcher-marshalled, gated on `StreamingIndicator.Visibility` so PTT chat doesn't paint UI; the streaming-send token loop flips back to `● Generating...` on first token. **Per-request `SemaphoreSlim` write-gate** added inside `/chat/stream` — the heartbeat fires from a thread-pool tick that can't await the response write without blocking, so the handler is fire-and-forget, but `HttpResponse.Body.WriteAsync` is not concurrent-safe; serializing all NDJSON writes through the gate (`start`, `loading`, `token`, `complete`, `rag-warning`, `error`) prevents interleaved bytes on the wire. **Boundary logs** added to `ChatService` via `SsdLogger.Info`: `chat stream begin`, `chat first-token in NNNNms`, `chat stream complete in NNNNms`, plus cancellation/error variants — durable evidence per the C1 backlog phase-1 ask, lands in the on-SSD log even when the user can't grab live diagnostics. **The heartbeat doubles as diagnostic + fix.** Three observable cases now: heartbeats flow then tokens arrive = healthy cold-load; heartbeats flow past 180s with no token = real Ollama-side load issue (memory pressure, corrupted blob, etc., user can stop and investigate); no heartbeats at all = sidecar broken before reaching `ChatService`. **Tests (2 new pins, +1 fixture extension):** `RunnerLocalApiServiceTests.ChatStream_HeartbeatRaised_EmitsLoadingFrameBeforeTokens` (start → loading×2 → token → complete frame ordering) and `ChatStream_NoHeartbeat_OmitsLoadingFrames` (warm-load contract pin so unknown-type-tolerant clients aren't surprised). `FakeChatService` gained `HeartbeatSecondsBeforeTokens` list + `FirstTokenPending` event so tests don't sleep 20s. ChatService heartbeat task itself is unit-tested only via the integration pin — extracting a clock seam for ~30 lines of cancellation-bounded loop is overkill. **Cross-OS bundle:** shared `runner-core` change auto-applies to both platforms; the new event signature broke compile on six `IChatService` implementations (production `ChatService` + `TestModeChatService` + four test stubs `FakeChatService`/`StubChat`/`StubChatService`×2). **CI required a second push** — initial pass missed two test stubs (`RunnerLocalApi{Library,StaticFiles}Tests.StubChatService`) because the `LogMessage`-keyed grep didn't catch them; the broader `: IChatService` grep would have. Second pass green on all three jobs (mac-prep 52s, mac-runner 55s, windows 3m4s). Decision pinned in `project_decisions.md`.
