- **PR #231 — MAC35a readiness skips AppleDouble sidecars on exFAT-prepped Mac SSDs — merged `8f3b54e` (2026-05-09).** Released as **v1.3.16**. Closed the v1.3.15 mac field-test readiness regression: PrepApp logged `Pulled qwen2.5:7b.` cleanly, then crashed readiness with `Command failed ('readiness'): '0x00' is an invalid start of a value`. Diagnosed: macOS auto-creates AppleDouble companion files (`._<tag>`) next to any file with extended attributes when the destination filesystem lacks native xattr support — exFAT qualifies. The user's SSD held a valid 858-byte `7b` manifest AND a 4 KB `._7b` AppleDouble blob (magic header `0x00 0x05 0x16 0x07`). `DiscoverModelsOnDisk`'s wildcard enumeration picked up both, `FindModelBlobForModel("qwen2.5:._7b")` resolved to the AppleDouble file, and the unhandled `JsonDocument.Parse` aborted the entire readiness command. Three protections in `prep-core/ModelOperations.cs`: filter `._*` in `DiscoverModelsOnDisk`, filter `._*` in `FindModelBlobForModel`, defensive try/catch around `JsonDocument.Parse` in `TrySelectModelLayerDigest` (mirrors the catch already in `EstimatePartialProgress`). Windows untouched (NTFS supports xattrs natively; sidecars never appear). 4 new tests — 3 unit, 1 end-to-end readiness pin. CI green on first run (mac-prep 48s, mac-runner 49s, windows 3m32s); v1.3.16 dispatch followed merge in the same session, all four jobs green, both ZIPs published.
