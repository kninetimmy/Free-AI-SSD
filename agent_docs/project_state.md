Closed the two false-negative reds on the v1.3.9 mac field-test readiness page (`Config.json valid` Fail + `≥1 installed model` Fail) on a drive that had successfully pulled `llama3.2:1b`. Three layered bugs in two files + one new test file. **Bug 1 (cross-OS path):** `PortableConfig.ConfigRelativePath` used `@"config\\portable-config.json"` — Windows `Path.Combine` collapsed `\\` mid-path by accident, but macOS treated it as a literal filename character, so `File.Exists` returned false on Mac before readiness ever opened the real config. Latent Windows bug closed too. **Bug 2 (encrypted config rejected):** Mac PrepApp ships only the encrypted blob per the MAC5 invariant; pre-MAC29 `ReadinessService` loaded the plaintext path only. Reworked `LoadConfigForReadinessAsync` to accept either: passes when the encrypted blob parses as JSON with the expected `scheme` field (no passphrase needed for the integrity check) or when the plaintext file loads cleanly. **Bug 3 (model status missing):** Mac sidecar's `pull-model` arm doesn't write back to the encrypted config (the passphrase is zeroized before pulls run). Switched the model check to disk-truth via `ModelOperations.DiscoverModelsOnDisk` + `FindModelBlobForModel`. Each blob is verified against its config-pinned SHA when one exists (preserves Windows' full-strength integrity guarantee), otherwise against its own filename digest — Ollama blobs are content-addressed by filename (`sha256-<hex>`) so the self-consistency check still catches tampering. Status writeback only happens when a plaintext config was loaded, so the encrypted-only Mac path never silently produces a plaintext file. Four new tests in `tests/ReadinessServiceTests.cs` pin: encrypted config + model on disk → all-green (the field-test regression pin); encrypted config + zero models → only model check fails; plaintext + pinned-SHA → unchanged Windows behavior; no config at all → both fail clearly.
